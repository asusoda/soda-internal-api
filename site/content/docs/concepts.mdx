## Organizations

An organization is one Discord server. Almost every route is under the organization's prefix, for example `/api/compute/robotics/pods`. Members are the people in the server. Officers hold the officer role the organization configured. Superadmins manage every organization on the deployment.

## Features

A feature is something Platform does for an organization, such as Points, Knowledge or Uptime. In the code, a feature is a module under `modules/`. Each feature is in one category: Core, Storage, AI and agents, Automations, Bots or Compute.

Core features, such as sign-in, Alerts and the MCP server, are always on. The others switch on or off for each organization on the Features tab of Explore. A new organization starts with each of them off. A feature that is off returns 404 for that organization, and the dashboard hides it. A feature keeps its logic in a Flask-free `service.py` that the REST API, the MCP server, jobs and the bot all use.

## Shared content

Shared content is made once for every organization, such as ASU's campus pages or the careers job sources. In the code, each one is a submodule under `submodules/`. An organization subscribes on the Shared tab of Explore, and each feature that is on gets its part: Knowledge searches the pages, and Feeds offers the feeds. The deployment crawls the pages once for every subscriber.

## Shared or isolated

| | Isolated | Shared |
| --- | --- | --- |
| Owner | One organization | The deployment |
| Examples | Its points, documents, pods, apps, monitors | Shared content, the Discord bot, the MCP server, the embedder |
| Counts against the organization's limits | Yes | Only its use, such as embeddings a day. Shared content does not count |

## Apps

An app is a program in its own container or pod, never a Platform process, such as an org's own Discord agent or a password vault. The Hosting page deploys the organization's apps, from a manifest or a template, and rolls them back. An app runs on RunPod with the organization's own key, or on This server as a capped container that the deployment provides. A shared app, such as the vault, runs once for the whole deployment: an organization subscribes on the Shared tab of Explore and gets its own space in it. Uptime watches any address, also one that Platform does not run. An app reaches Platform over MCP with a token of its organization.

## Limits

All organizations share the same processes and database. Each feature declares limits, such as knowledge sources, pods or tool calls a minute. Each limit says who pays: the organization's own data, or its use of a shared service. Each container also has a memory and CPU cap. The superadmins see each organization's use and the server's health, and set the limits of each organization. See [Limits](/docs/codebase/limits).

## Access

People sign in with Discord. Every organization route checks whether the caller is a member, an officer or a superadmin before it runs. Changes made by officers and tokens are written to the audit log.

Programs use machine tokens instead of a login. A token starts with `plat_`, is stored only as a hash, belongs to one organization, and carries scopes such as `knowledge:read` or `godfather:connect`. Agents, deploy pipelines and the godfather CLI each hold one.

## Secrets

Per-organization credentials (a RunPod key, a Google service account, OAuth grants) are encrypted with `SECRETS_KEY` and stored in the database. They are never returned by the API.

## Jobs

Background work is declared with `@job` in each module's `jobs.py`. On Postgres a separate worker process runs them from a Procrastinate queue. On SQLite they run in threads inside the API process. Examples are the daily LeetCode post, crawls, pod session start and stop, and token cleanup.
